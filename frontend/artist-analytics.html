Roadmap: Expanding Analytics

The metrics above are the foundation. Here is exactly how each dimension can be extended — each card maps to a concrete backend change and a specific IBM technology integration.

▶

Streaming Analytics

Every time a fan clicks Stream ↗ on a release, publish a release.streamed event. A lightweight stream_event table stores artist_id, release_id, fan_id, streamed_at.

The analytics endpoint gains new keys: total_streams, streams_last_30_days, top_release, streams_by_release[].

IBM Confluent (Kafka): stream events flow through a Kafka topic in real time — no polling, no DB writes in the hot path. A consumer microservice batches and persists them, keeping the Flask API responsive under load.

$

Sales Analytics

The order table (already in the data model) records fan_id, item_type, item_id, quantity, unit_price. Aggregating it unlocks: total_orders, total_revenue, revenue_last_30_days, top_product.

Revenue is stored as NUMERIC(10,2) to avoid floating-point rounding errors — the same pattern already used in merch_product.price.

OpenShift: deploy the Flask API and a separate orders worker as independent pods. The orders service scales independently during merch drops without touching the profile or analytics pods.

↑

Audience Analytics

Extend the existing follow table with a source column ("browse", "recommendation", "share") and a nullable unfollowed_at for churn tracking. This gives: new_followers_last_30_days, churn_rate, follower_locations.

A fan engagement score combines follows, streams and orders into a single composite metric — useful for prioritising which fans to reach out to for early access drops.

IBM watsonx AI: pass the snapshot to watsonx.ai text generation to produce a plain- English summary: "Streams are up 42% this week. Consider posting more content — artists with 3+ posts/week see 18% higher follower growth."
